## 1. 專案目的

EMS 與 MSD 跨部門的需求管控表。流程有順序：

```
① EMS 提供 Spec → ② MSD 確認沒問題 → ③ MSD 壓開發日期 → ④ EMS 驗收 → 結案
```

EMS 也可以先壓預設的驗收時間，或等開發完再填。

**高階主管的核心需求**（設計時的第一優先）：
1. 清楚知道需求是**什麼時候建立**的
2. 規格填完後**是否被異動過**，有異動就要留下可追蹤的紀錄

| StatusID 不可空白 | `17_stagecode_not_null.sql`；匯入空白由 `InferStageCode()` 推一次寫進去。H4（匯入後跑不變量檢查）**使用者沒選、沒做** |
| 逾期判定 | **只有一份規則 `isPhasePassed()`**。`resolveDuePhase()` = 排除走完的階段 → 剩下有日期的取**到期日最早**的。⚠️ 不可改回「四個日期一起比」；⚠️ 也不可加回「退回最後一個已排定的階段」；⚠️ **「走完了沒」只看 StatusID，不可再加回任何「下一階段有日期 → 這階段走完」的反推** |

**這條資料鏈的四個關節（要動它們之前先看這裡）**：
1. **`init` 不算異動** —— 所有次數統計一律 `WHERE ChangeType <> 'init'`，否則每筆資料光是建立就掛上 ⚠1
2. **gating 只擋「從空白開始填寫」** —— 已有值的欄位照舊可解鎖修改，否則階段跳空的資料會有值卻永遠改不動
3. **延期完成時 End 不動、只寫 `ActualEnd`** —— 所以畫面一定要同時呈現「原訂 → 實際」
4. **三個計數欄是稽核表的 denormalized 快取** —— 徽章與排序直接讀欄位不 parse 稽核表；但**事實以稽核表為準**，不一致時以稽核表去修計數欄

## 5. 這台機器與驗證方法的坑

### 工具
- ⚠️ **`python` 是 Windows Store 的假殼**，什麼都不做也不報錯 —— 改檔一律用 **node**（或 Edit 工具）。
- ⚠️ **`Get-Content` / `Set-Content` 會把含中文的檔案燒成亂碼且不報錯** —— 改檔一律用工具、`sed -i` 或 node。
- ⚠️ **`node -e` 在 Git Bash 裡**：路徑寫 `C:/Controltable/...`，**不可寫 `/c/...`**（會變成 `C:\c\...`）；
  regex 裡的 `\/` 跳脫會被 shell 吃掉變成 `///g`（Babel 直接解析失敗）—— 改用 `split('/').join('-')`。
  大段替換用「讀檔 → `split(舊).length` 確認剛好 1 次 → replace → 寫回」，單引號用 `\x27`。
- ⚠️ **curl 在 Git Bash 送中文 JSON 會被燒成 Big5 而 400** —— 送中文用 node 的 `fetch`。
- ⚠️ **sqlcmd 畫面上的中文一定是亂碼**（console Big5）；要驗中文看 API 的 JSON 或 `-f 65001`／`-o` 導檔。
- ⚠️ **sqlcmd 跑 DML 一定加 `-I`**（QUOTED_IDENTIFIER；`IX_Controltable_Active` 篩選索引會讓 DELETE／UPDATE 直接 `Msg 1934` 失敗）。
- ⚠️ **grep 中文找 `wwwroot/app.js` 會找不到** —— Babel 會把部分中文輸出成 `\uXXXX`。確認新程式有沒有進去改用 node
  `includes()` 找 ASCII 的識別字（例：`nextWeekCount`）。
- ⚠️ **`npm run build` 偶爾遇 `UNKNOWN: unknown error, open`**（app.js 被鎖），重跑就好 —— **build 失敗時產物是舊的**，一定要確認有新符號。

## 8. 使用者的溝通偏好

- **檢查邏輯／體檢類的工作：先分級出清單，讓他挑做哪幾組**，不要直接開始改。
  **沒挑中的要留證據**（就是第 3 節與第 4 節）。**下一輪要重新分析，不要照抄舊表。**
- 回報 UI 問題時他常附截圖，而且用詞很直接（「變成兩行了!!」「看起來像是網頁哪邊壞了」）——
  那通常代表**畫面上有一個他當下修不了的東西**，先量再答。
- 他會**改主意**（事後補記、第三個頁籤、EMS 身分篩選都是）。改主意時不要拿舊紀錄回頭擋他，
  但**當年否決的理由通常仍然成立**，要把它翻譯成新做法的界線。
- 改到**畫面上看得見的行為**就要一併更新 `docs/使用者手冊.html`（判斷標準是「畫面上會不會不一樣」，
  純內部重構不算）。手冊抬頭那個「版本」要手動對齊當次的 `?v=`。
- **他幾乎每一項都要先看示意圖**（「先給我預計修改後的 UI 示意圖」「再重新給我一版」）—— 改 UI 之前先畫，
  他會來回調幾輪（名稱、顏色、字數）才說「照這版改」。示意圖要畫**實際會出現的字與數字**，圖例用的說明卡片要講明「信裡不會有這個」。
- 他常用「這樣合理嗎?」「有點突兀」「字有點多」開頭 —— 先承認問題、給一個**推薦**和理由，再列替代方案；不要只列選項。
- 寫給他的說明要短、用畫面上的字；技術名詞（函式名、檔名）留在 CLAUDE.md／memory.md，不放進回覆正文。
